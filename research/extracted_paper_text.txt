Abstract – IoT development and testing often require multiple
physical sensors, which increases hardware cost, wiring com-
plexity, configuration effort, and maintenance requirements.
Testing an IoT application under different environmental con-
ditions or sensor failure situations is also difficult because such
conditions are not always safe or easy to reproduce. This pa-
per presents OneSensor, an ESP32-based virtual multi-sensor
platform designed to provide configurable sensor inputs for
IoT development and testing. The proposed system uses an
ESP32 as a virtual sensor device capable of generating values
representing sensors such as temperature, humidity, gas, light,
and soil moisture, and the current prototype extends this set to
twelve concurrently addressable channels. These values can
be provided to an external device such as an Arduino UNO,
which acts as the system under test. A web-based dashboard
allows the user to configure virtual sensors, assign sensors to
output channels, select environmental scenarios, and introduce
controlled sensor faults. The proposed approach enables re-
peatable testing without requiring a separate physical sensor
for every development stage. The platform also provides a
foundation for future machine-learning-based sensor models,
protocol-level sensor emulation, and automated testing. One-
Sensor therefore aims to provide a low-cost and reusable plat-
form for controlled IoT experimentation and Hardware-in-the-
Loop testing.
Index Terms – fault injection, IoT testing, sensor emula-
tion, sensor virtualization, virtual sensors, hardware-in-the-
loop testing
1. Introduction
The Internet of Things has become an important technol-
ogy for applications including smart homes, agriculture, indus-
trial monitoring, environmental monitoring, healthcare, and au-
tomation. These applications depend heavily on sensor data
to observe physical conditions and make decisions. During
the development of such systems, developers generally require
several physical sensors to reproduce the inputs expected by
the application. This increases the overall cost of prototyping
and introduces additional wiring, calibration, power, and main-
tenance requirements.
Another important challenge is testing an IoT application
under different environmental and abnormal conditions. A de-
veloper may need to determine how an application behaves
when temperature increases rapidly, gas concentration rises,
soil moisture decreases, communication is interrupted, or a
sensor produces incorrect values. Reproducing these condi-
tions using physical sensors can be difficult, unsafe, and incon-
sistent. Furthermore, repeatedly testing the same failure condi-
tion may require manually changing the physical environment
or disconnecting hardware components.
Virtual sensing and sensor virtualization have been investi-
gated to reduce the dependence on direct physical sensing re-
sources. Yuriyama and Kushida proposed a Sensor-Cloud In-
frastructure in which physical sensors could be represented and
managed through virtual sensor objects [1]. Perera et al. in-
troduced CA4IOT to provide context-aware configuration and
processing of sensor information according to user require-
ments [2]. Their work demonstrates how higher-level context
can be used to simplify interaction with large numbers of sen-
sors.
Perera et al. later proposed a Mobile Sensor Hub that sup-
ported dynamic configuration of heterogeneous sensors and
communication between sensor devices and middleware [3].
Bose and Mukherjee proposed SensIaaS, extending the con-
cept of sensor virtualization into a sensor-cloud infrastructure
[4]. Chatterjee et al. developed a Big-Sensor-Cloud Infrastruc-
ture for provisioning sensing resources as a service [5]. More
recently, Zaidan et al. investigated virtual sensors for high-
resolution air-pollution monitoring using artificial intelligence
and IoT [6]. Complementary to the cloud-oriented virtual-
sensor literature, a separate body of work on Hardware-in-the-
Loop (HIL) simulation has studied how to electrically emulate
sensors and actuators so that an embedded controller under test
perceives a physically realistic signal rather than a purely soft-
ware value [7, 8], and a further line of research studies how
faults can be deliberately injected into such emulated signals
or into the target system itself to evaluate reliability and fail-
safe behavior [9, 10, 11].

Although these studies establish important concepts related
to virtual sensors, context awareness, dynamic configuration,
and intelligent sensing, the proposed OneSensor system fo-
cuses on a different application. Instead of primarily managing
physical sensors through cloud infrastructure or estimating an
unavailable physical measurement, OneSensor uses an embed-
ded ESP32 device to generate controllable virtual sensor inputs
for another IoT device. The ESP32 acts as the virtual sensing
platform, while an Arduino UNO or another controller can act
as the system under test.
The proposed platform combines virtual sensor generation,
configurable sensor-to-channel mapping, environmental sce-
nario simulation, fault injection, and browser-based control.
This combination allows developers to test IoT applications
under controlled conditions without requiring all correspond-
ing physical sensors during the early stages of development.
Compared with the initial concept, the current prototype addi-
tionally realizes the virtual-sensor-to-target link as a genuine
electrical signal – pulse-width-modulated (PWM) pulses and
an on-chip digital-to-analog converter (DAC) voltage – carried
over physical wires to the target microcontroller’s input pins,
which places OneSensor firmly within the HIL tradition of
electrical sensor emulation [7, 8] rather than a purely software-
level mock.
2. Related Work
Sensor virtualization provides an abstraction between sens-
ing resources and applications. Yuriyama and Kushida intro-
duced a Sensor-Cloud Infrastructure that represents physical
sensing resources through virtual sensors and virtual sensor
groups [1]. Their architecture enables users and applications
to provision and manage sensing resources without directly in-
teracting with individual physical sensors. This concept is rele-
vant to OneSensor because the proposed system also represents
different sensing capabilities through virtual entities. However,
the objective of OneSensor is not cloud-based management of
physical sensors. Instead, the ESP32 itself generates the sen-
sor values and provides them as controlled inputs to an external
IoT system.
CA4IOT proposed by Perera et al. focuses on context
awareness in IoT systems [2]. The system attempts to reduce
the complexity of selecting appropriate sensor information by
understanding high-level user requirements and automatically
configuring sensor filtering, fusion, and reasoning. This work
is related to the scenario-based operation of OneSensor be-
cause a selected environment can influence the behavior of
multiple virtual sensors. However, CA4IOT primarily focuses
on context-aware sensor information processing, whereas One-
Sensor uses environmental scenarios to generate controlled test
inputs.
Dynamic sensor configuration was further explored by Per-
era et al. through the Mobile Sensor Hub approach [3].
Their system provides a mechanism for connecting external
sensors and configuring communication between sensor de-
vices and middleware. This is relevant to OneSensor’s con-
figurable sensor-to-channel mapping, where the user can deter-
mine which virtual sensor should be associated with a partic-
ular output channel. The important distinction is that the Mo-
bile Sensor Hub works with physical sensors, while OneSensor
generates virtual sensor values.
SensIaaS introduced sensor virtualization within a sensor-
cloud infrastructure [4]. The work demonstrates how virtual-
ized sensing resources can be managed as services and made
available to applications. Similarly, the Big-Sensor-Cloud In-
frastructure proposed by Chatterjee et al. investigates large-
scale provisioning of heterogeneous sensing resources as ser-
vices [5]. These systems demonstrate the scalability and flex-
ibility of cloud-based sensor abstraction. OneSensor instead
focuses on a compact embedded platform that can be directly
used during IoT hardware development and testing.
Zaidan et al. investigated virtual sensors for high-resolution
air-pollution monitoring using artificial intelligence and IoT
[6]. Their approach demonstrates how virtual sensing can es-
timate environmental information using computational models
and available data. This work provides motivation for the fu-
ture extension of OneSensor toward machine-learning-based
sensor behavior. In the proposed system, however, the primary
purpose of the virtual sensor is not environmental estimation
but controlled generation of test inputs for IoT applications.
2.1 Hardware-in-the-Loop and F ault-Injection Literature
A second, largely disjoint body of literature studies HIL test-
ing as a general methodology for embedded and control sys-
tems. Abdalla et al. describe a low-cost HIL framework built
around a commodity analog/digital I/O card and Simulink, ex-
plicitly modeling delay, noise, and saturation so that a con-
troller under test experiences realistic, non-ideal signals rather
than an idealized simulation [7]. National Instruments’ HIL
test-system architecture similarly emphasizes electrical load
and sensor emulation together with deterministic real-time I/O
as the two pillars of a credible HIL rig [8]. OneSensor adopts
the same principle – physically realistic PWM/DAC signals
over real wires – but targets a very different price and complex-
ity point, replacing PXI/CompactRIO-class real-time hardware
with a single low-cost ESP32 module.
On the fault-injection side, Elgharbawy et al. propose a
generic architecture for injecting faults into virtual sensor sig-
nals for Advanced Driver Assistance System (ADAS) testing,
arguing that fault realism at the signal layer is essential for
validating perception pipelines [9]. Magliano et al. present
a configurable fault injector that manipulates a CPU’s micro-
architectural state (registers and RAM) through a JTAG de-
bug interface for reliability assessment of safety-critical em-
bedded software [10], while Skarin et al.’s GOOFI-2 tool pro-
vides a generic, campaign-based framework for injecting faults
and collecting dependability measurements across heteroge-
neous target platforms [11]. These frameworks operate pri-
marily at the processor/memory level or at the level of a simu-
lated perception signal; OneSensor is instead positioned at the
physical analog/PWM sensor-interface layer that sits between
a virtual sensor model and a real target microcontroller’s input
pins, which is a comparatively underserved point in the fault-

3. Problem Statement and Research Gap
IoT applications often require multiple sensors during devel-
opment and testing. Using physical sensors for every required
input increases prototype cost and makes the testing process
more complicated. In addition, environmental conditions such
as fire, gas leakage, flooding, extreme temperature, or abnor-
mal sensor behavior are difficult to reproduce safely and re-
peatedly. Existing sensor virtualization research has mainly
concentrated on virtual representations of physical sensing re-
sources, cloud-based sensor management, context-aware pro-
cessing, dynamic sensor configuration, and virtual estimation
of environmental measurements.
The research gap addressed by OneSensor is the integra-
tion of virtual sensor generation and controlled Hardware-in-
the-Loop testing on a low-cost embedded platform. The pro-
posed system allows multiple sensor types to be represented
by software-generated values on an ESP32 and provides mech-
anisms for changing their configuration, environmental behav-
ior, and fault conditions. The same platform can therefore be
reused for different IoT projects without requiring a separate
physical sensor set for every application.
OneSensor also addresses the problem of reproducibility. A
particular sensor condition can be generated repeatedly using
the same configuration. This is useful for testing applications
under abnormal conditions because the developer can repro-
duce the same sensor behavior without physically recreating
the corresponding environmental event.
4. Proposed System
OneSensor is proposed as an ESP32-based virtual multi-
sensor platform for IoT development and testing. The central
idea is to use the ESP32 as a virtual sensing device rather than
connecting a separate physical sensor for every measurement
required by an IoT application. The ESP32 generates sensor
values according to predefined models and sends the generated
values to an external device that represents the system under
test.
The initial virtual sensor set consists of temperature, humid-
ity, gas, light, and soil moisture. Each sensor has a configurable
range and behavior model. Instead of producing completely
random numbers, the system can generate time-dependent val-
ues that change gradually under normal conditions. The gen-
erated value can subsequently be modified according to the se-
lected environmental scenario or fault condition.
The proposed architecture consists of a web dashboard, con-
figuration manager, scenario engine, virtual sensor models,

fault injection engine, channel manager, and output interface.
The user interacts with the dashboard through a browser. The
selected configuration is processed by the ESP32, which gen-
erates the corresponding virtual sensor values and routes them
through the configured output channels. Fig. 1 shows this con-
ceptual flow.
One of the important features of OneSensor is dynamic
sensor-to-channel mapping. The user can select a virtual sensor
and assign it to a particular output channel from the dashboard.
This provides flexibility because the same ESP32 platform can
be configured differently for different IoT projects. For exam-
ple, a temperature model may be assigned to one channel dur-
ing one experiment and replaced by a gas model during another
experiment without changing the core hardware.
The system also introduces scenario-based simulation. A
scenario represents an environmental condition in which multi-
ple sensor values may change together. For example, a fire sce-
nario can produce increasing temperature and gas values, while
an agriculture scenario can produce variations in soil moisture,
temperature, humidity, and light. This relationship between
multiple sensor values provides more meaningful test data than
independent random-value generation.

The second layer is the configuration manager. It stores the
current sensor selection and channel mapping. Each output
channel can be associated with a particular virtual sensor ac-
cording to the requirements of the IoT application being tested.
This allows the same physical OneSensor device to support dif-
ferent application configurations.
The third layer contains the virtual sensor models. Each
model is responsible for generating values corresponding to
a specific sensor type. The models can use predefined
ranges, gradual changes, relationships between variables, and
scenario-specific behavior. The generated values are passed to
the fault injection layer before being delivered to the output
interface. As summarized in Table 2, the current prototype im-
plements twelve concurrently addressable channels, each de-
scribed by a configuration record giving its output GPIO, signal
type, dynamic range, default value, and calibration factors.
The fourth layer is the scenario and fault injection layer. Sce-
narios modify sensor behavior according to predefined envi-
ronmental conditions. Fault injection intentionally introduces
abnormal behavior such as noisy data, stuck values, sudden
spikes, sensor offline conditions, or delayed transmission.
The final layer is the output interface. It transfers the gener-
ated values from the ESP32 to the external system under test.
In the prototype, an Arduino UNO can be used as the receiving
device. The Arduino processes the incoming sensor values as
inputs for the application being tested; a companion decoder
library recovers the pulse duty cycle (for PWM channels) or
the sampled analog voltage (for DAC channels) and converts it
back into the original engineering unit through the inverse of
the linear mapping applied on the ESP32 side.
6. Fault Injection and Testing
Fault injection is included to evaluate how an IoT applica-
tion responds to abnormal sensor conditions. The system can
intentionally introduce conditions such as sensor offline behav-
ior, noisy readings, stuck values, sudden spikes, gradual drift,
and delayed transmission. Because these faults are software-
controlled, the same condition can be reproduced multiple
times during testing.
A normal sensor value can be represented as
S(t) =B + T (t) +E(t) +N(t), (1)
where B is the baseline value, T (t) represents the time-
dependent component, E(t) represents the environmental sce-
nario, and N(t) represents controlled variation.
The fault injection layer transforms the normal value accord-
ing to the selected fault condition. For example, a spike fault
can temporarily increase the value, while a stuck-sensor fault
can maintain a previously generated value for a specified pe-
riod. Table 3 summarizes the seven fault classes implemented
in the current prototype and the transformation each applies
to the incoming value before it reaches the output interface,
shown schematically in Fig. 3.
The testing process follows a Hardware-in-the-Loop con-
cept. The ESP32 generates the virtual sensor input while the
Arduino UNO executes the application logic normally used
with sensor data. The developer can therefore evaluate the be-
havior of the external application under normal, environmental,
and faulty conditions.

7. Implementation
The prototype is implemented using an ESP32 development
board and an Arduino UNO. The ESP32 is the primary One-
Sensor device and is responsible for virtual sensor generation
and configuration. The Arduino UNO is treated as the external
system under test. The initial implementation establishes the
communication path between the two devices before progres-
sively adding the complete dashboard and simulation features.
In the initial stage, the ESP32 generates a virtual sensor
value and provides an equivalent electrical output that can be
read by the Arduino. This approach validates the basic concept
that software-generated sensor information can be supplied to
another microcontroller as an input. The signal path is there-
fore ESP32 virtual sensor generation, output interface, Arduino
input, and application processing.
The ESP32 provides Wi-Fi connectivity that can be used for
communication with the browser-based dashboard. HTTP can
be used for dashboard requests and configuration, while Web-
Socket communication can provide real-time updates of gener-
ated sensor values. MQTT can optionally be supported for ex-
ternal IoT integration. Table 5 summarizes the software stack
used across the two ends of the current prototype.
Fig. 4 and Fig. 5 indicate the intended layout of the two pri-
mary dashboard views once the browser-based front end is fi-
nalized: a live telemetry view showing the twelve virtual chan-
nels, and a configuration view for sensor-to-channel mapping
and fault arming.
The system is designed in a modular manner so that the vir-
tual sensor generation layer is independent of the dashboard
and output layer. This makes it possible to add additional vir-
tual sensors without redesigning the complete system. It also
provides a foundation for future machine-learning-based sen-
sor models.
8. IoT Technology and Communication
The ESP32 is selected as the main controller because it pro-
vides sufficient processing capability, Wi-Fi connectivity, mul-
tiple GPIO interfaces, and a low-cost development platform
[12, 13]. Wi-Fi enables the OneSensor device to communicate
with a browser-based dashboard without requiring additional
networking hardware.
HTTP is suitable for configuration and dashboard requests
because it provides a simple communication mechanism be-
tween the browser and the ESP32. WebSocket can be used
when continuous real-time sensor updates are required because
it allows persistent communication between the dashboard and
the device. MQTT can be considered for future integration
with external IoT platforms where a publish-subscribe com-
munication model is required.

10. Future Scope
The current architecture provides several possibilities for fu-
ture development. Machine-learning-based virtual sensor mod-
els can be introduced by training models using real sensor
datasets. Instead of relying only on mathematical equations,
the system could learn temporal patterns, correlations between
sensors, and realistic variations from recorded measurements.
This can improve the realism of generated sensor data.
Another direction is protocol-level sensor emulation. Future
versions can investigate emulation of interfaces such as I2C,
SPI, UART, and OneWire communication. This would allow
OneSensor to test applications that depend on existing sensor
libraries without requiring the actual sensor hardware.
The dashboard can also be extended with automated test se-
quences. A developer could define a sequence containing nor-
mal operation, scenario changes, fault injection, recovery, and
data logging. The platform could execute the sequence auto-
matically and generate a report of the observed system behav-
ior.

Additional future work includes cloud integration, mobile
monitoring, more virtual sensor models, dataset-based scenario
generation, a plugin architecture through which developers can
add new sensor models without modifying the core system, and

of the HIL evaluation methodology reported for commodity
ADDA-card rigs [7] – to quantify end-to-end latency, jitter, and
decoder overhead on physical hardware.
11. Conclusion
OneSensor presents a low-cost ESP32-based approach for
virtualizing multiple sensor inputs for IoT development and
testing. The proposed system uses the ESP32 as the main vir-
tual sensor device and an Arduino UNO or another controller as
the system under test. By generating configurable sensor val-
ues, the platform can reduce dependence on multiple physical
sensors during the development stage.
The combination of sensor-to-channel mapping, environ-
mental scenario simulation, fault injection, and browser-based
configuration provides a controlled environment for testing IoT
applications. Unlike approaches that primarily focus on cloud-
based sensor management, OneSensor focuses on providing
virtual sensor inputs directly to an embedded IoT system, and
unlike fault-injection frameworks that target processor state or
simulated signals, OneSensor injects faults directly into the
physical sensor-interface layer seen by the target device.
The current prototype establishes the fundamental ESP32-
to-Arduino testing concept across twelve virtual sensor chan-
nels, while future development will extend the platform toward
more accurate sensor protocol emulation, machine-learning-
based sensor behavior, automated test sequences, and cloud
connectivity. The proposed platform therefore provides a prac-
tical foundation for low-cost, reusable, and repeatable IoT de-
velopment and testing.
